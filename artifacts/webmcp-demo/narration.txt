Open the WebMCP command center. This page explains the browser-native surface and shows its current size: twenty-one tools, fourteen read-only, and six that require a human-governed decision.

Open the authenticated workspace. Here, document dot model context registers the tools against the signed-in user's session. The browser receives schemas and annotations, but it never receives a separate OrgMemory credential.

The browser calls list OrgMemory spaces first. It then calls get OrgMemory briefing for one concrete task: raise worker concurrency on the payments service from a deployment console. These are page-defined WebMCP calls, not REST requests relabeled for the demo.

The briefing returns six relevant memories and a requires-approval verdict. It retrieves the previous pool-exhaustion incident, the shared PostgreSQL dependency, the concurrency-cap decision, and the first-response procedure. The activity panel records each tool name, arguments, result count, and latency.

The investigation continues with incident, dependency, and decision tools. The first agent can now explain the failure mode and the blast radius from structured company memory instead of scraping text from several screens.

When the agent derives a new verified incident, it can only create a proposal. The record says that nothing is saved yet. A person reviews the evidence and decides whether it enters company memory.

Start session two. This is a different agent with no shared chat and no carried prompt context. It retrieves the approved procedure, incident history, service context, and prior decision because OrgMemory persisted them outside the first session.

The rest of the application builds and maintains that memory. Add Knowledge accepts pasted documents, repositories, Slack channels, and connected sources. The original source is preserved before extraction begins.

The Memories view shows the resulting atomic records. Each incident, procedure, dependency, and decision has its own type, confidence, scope, validity, and current-state status instead of being stored as one summary blob.

Profiles are assembled at request time from current authorized memories. This payments profile contains the active concurrency decision, the response procedure, and the shared PostgreSQL dependency.

The Memory Graph connects sources, revisions, memories, entities, services, and relationships. It supports provenance checks, related-memory traversal, updates, contradictions, ownership, and dependency reasoning.

Memory Work turns selected context into an output package. The user describes an outcome once; OrgMemory activates current evidence, prepares the work, and keeps connector actions behind explicit approval.

The Outcome Loop records which context was served, what action followed, and whether it worked. The briefing from this demo appears as an open ledger row. Record OrgMemory outcome closes the row without silently changing company memory.

That is the application flow shown here: ingest sources, extract governed memory, retrieve it through WebMCP, require human decisions for writes, prepare work, and record outcomes for the next agent.
